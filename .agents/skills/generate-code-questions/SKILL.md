# Generate Code Questions

把用户指定的代码作为题目来源，把问题组织成一条 top-down 阅读路径：先建立高层地图和流程骨架，再逐段深入实现，最后把细节重新串成端到端流程。目标是帮助学习者建立完整代码心智模型，不是生成知识测验、面试题或只关注缺陷的审计清单。

## 核心原则

- 以目标代码、构建配置、测试和当前版本行为为最终依据。外部文档和通用知识只用于理解背景，不能替代源码证据。
- 先帮助学习者回答“系统解决什么问题、边界在哪里、主要组件如何协作”，再进入入口、对象和实现细节。
- 根据前置知识和端到端流程排列问题。每个局部问题都应落在流程骨架的某个阶段，最后的综合问题应复用前面形成的理解。
- 根据代码库实际存在的语言、架构、运行模型和错误机制调整分析维度，不要强行寻找不存在的复杂性。
- 遵循用户指定的范围、语言、数量和输出形式，不假设固定目录或文件名。
- 只生成问题和必要的阅读起点。除非用户明确要求，否则不要同时回答问题。
- 用户没有要求写文件或没有提供可推断的目标位置时，在回复中返回草稿，不要自行创建文档目录。

## 生成流程

### 1. 明确学习目标与范围

确定学习者想理解的代码范围、使用场景和已有知识。用户未说明水平时，默认面向“具备基本编程能力，但不了解当前实现”的读者；不要把领域术语当作已知前提。

明确待分析的代码片段、仓库、目录、模块、变更集、执行场景或问题数量。范围不明确时，选择一个能够从入口追踪到结果的内聚单元，并说明该假设；不要把大范围内的零散观察拼成一组问题。

读取适用的项目指令、构建文件、公开接口、实现、数据定义和测试。在版本库中工作时，先检查工作树状态并保留已有改动。使用代码搜索确定定义、调用者、被调用者和跨模块引用，不要只按文件名或目录名推断行为。

### 2. 建立代码事实图

在写问题前，记录与当前范围相关的事实：

- 对外目标、输入输出、系统边界、主要组件及职责；
- 从外部入口经过关键阶段到最终结果的流程骨架；
- 核心数据结构及其创建、变换、发布、持久化、转移与销毁；
- 对象状态机、跨函数不变量以及状态对其他组件的可见边界；
- 线程、任务、事件循环、锁、原子操作或消息传递等实际存在的并发关系；
- API、协议、存储、进程、设备、编译器或运行时等组件边界；
- 错误返回、异常、取消、超时、回滚、重试和部分副作用；
- 能够直接支持每项结论的符号、文件和测试。

只记录当前代码确实包含的维度。沿实际控制流和数据流阅读，不要把注释中的意图误当成已实现的行为。

### 3. 选择学习地标

先选择能够建立高层地图的代码关系：

- 代码对外提供什么行为，接收什么输入，产生什么输出；
- 系统边界内有哪些主要组件，它们各自承担什么责任；
- 一个典型场景从入口到结果依次经过哪些关键阶段。

再沿流程骨架选择需要深入的局部关系：

- 哪些对象承载核心数据，它们的状态如何随各阶段变化；
- 各阶段由哪些函数、算法或接口实现；
- 数据或控制何时跨越模块、线程、存储或外部接口边界；
- 某个顺序、检查、契约或同步约束为何存在；
- 成功与失败路径的提交点、清理责任或可见副作用为何不同；
- 边界值、容量、配置或隐含前提改变时会发生什么；
- 实现与公开 API、测试、注释或常见直觉为何存在差异。

最后选择一个能够重新串联全部关键阶段的具体场景，作为综合问题的依据。基础问题也必须要求阅读实现，例如从公开入口定位组件协作；不要退化为“某函数有什么作用”或术语释义。不要为了满足固定主题或数量而制造问题。

### 4. 安排渐进式阅读顺序

按以下依赖关系排列候选问题，并只保留当前代码实际需要的层次：

1. **高层总览**：理解目标、输入输出、系统边界、主要组件和职责，不先陷入函数细节。
2. **流程骨架**：以典型场景 breadth-first 地追踪入口、关键阶段和结果，只建立全貌。
3. **局部深入**：沿流程先后顺序逐段研究核心对象、状态变化、算法和接口实现。
4. **横切机制**：在主流程模型上理解跨阶段的不变量、并发、资源责任和失败处理。
5. **全流程串联**：使用具体输入或事件，综合前面结论，重新解释从入口到结果的完整控制流、数据流和关键状态。

流程骨架必须先广后深，不要在第一个阶段的细节尚未解释完时丢失后续阶段的全貌。局部深入题应按它们在端到端流程中的位置排序，而不是按源码目录排序。

不要在学习者尚未建立正常路径时先问失败回滚，也不要在引入某个符号前要求解释它的深层不变量。最终串联题不得突然引入新的核心概念，只能整合前面已经建立的知识。范围很小时可以合并相邻层次，但仍要先总览、再细节、最后综合。

### 5. 将地标改写成问题

把每题绑定到具体入口、符号、对象或执行场景，并给出足以开始阅读的源码锚点。优先追问：

- 这部分代码对外完成什么目标，主要组件和边界如何划分？
- 从某入口到某结果，流程依次经过哪些关键阶段，各阶段如何衔接？
- 某对象在主流程中由谁创建、修改、传递和消费？
- 两个组件通过什么接口协作，边界两侧各自保证什么？
- 某条件、顺序、契约或责任为什么存在？破坏它会产生什么可观察结果？
- 同一操作在成功、失败、取消或并发交错下分别提交了什么，又由谁清理？
- 给定一个具体场景，如何把所有关键阶段、对象变化和组件边界串成完整执行过程？

每题只围绕一个中心关系。只有多个分支用于比较同一语义时才合并；需要追踪互不依赖的入口、对象或责任时，拆成多题。

使用用户要求的语言。题干要明确下一步应追踪的代码关系，但不要暗示答案，不要把未验证的反事实写成事实。

### 6. 校验单题与学习路径

只收录满足以下条件的问题：

1. 题目中的入口、状态、边界或失败情形真实存在于当前代码。
2. 答案需要阅读相关实现和状态变化，而不是仅查名称或一处注释。
3. 题目能定位到明确的源码锚点，并在适用时通过测试、日志、跟踪、调试器或静态证明验证。
4. 题目之间不重复；更新现有题集时，修订或删除前提已经失效的问题。

同时检查整组问题：

- 第一批问题能否让陌生读者说清目标、边界、主要组件和输入输出；
- 流程骨架是否在深入细节前展示了从入口到结果的所有关键阶段；
- 每个局部深入题是否对应骨架中的明确阶段，并使用了前面已经建立的概念；
- 最后的综合问题是否要求复用此前结论，而不是引入新的隐藏前提；
- 完成整组问题后，读者能否从高层目标讲到实现细节，再独立重建完整流程；
- 正常路径、设计理由与异常路径的比例是否服务于理解，而不是全部集中在边缘情形。

### 7. 输出结果

遵循用户指定的输出形式。未指定格式时，先说明学习目标，再按阅读顺序列出问题和源码入口；问题较多时，按“高层总览、流程骨架、局部深入、横切机制、全流程串联”分组。

写入已有题集时：

- 读取目标文件的标题、编号、分组、链接和语言约定；
- 保持稳定编号，不因新增问题重排无关条目；
- 列出实际追踪过的源码入口，并在仓库文档中优先使用相对路径；
- 仅在目标题集已有索引、计数或配套资料区时同步维护它们；
- 保留用户已有改动，不创建与目标格式无关的辅助文档。

不要把事实图、推导过程或答案伪装成题目内容。阅读提示只能指出起始符号、调用方向或应观察的状态，不能提前给出结论。

## 质量检查

完成前确认：

- 所有问题都由实际代码观察产生，而非预设题库；
- 问题顺序能引导读者从高层地图进入局部实现，再回到端到端综合；
- 深入题沿流程骨架排列，最后至少有一个综合问题串起关键阶段；
- 每题聚焦一个中心关系，并提供可开始阅读的源码锚点；
- 没有函数用途复述、通用知识问答、重复问法或无证据假设；
- 没有在基础模型建立前堆叠反事实、并发和失败问题；
- 输出适配目标项目，而 skill 本身不依赖特定语言、框架、目录或文档结构；
- 代码变化后，题目前提、阅读顺序、源码锚点、链接和索引仍然有效。

验证所修改的文档、链接和结构。只有题目前提依赖运行时行为，或用户明确要求时，才运行相应的定向测试；不要默认运行整个项目的测试套件。
